## نظرة عامة

يستخدم المشروع بيانات **Global Terrorism Database (GTD)** لتحليل الحوادث المسجلة تاريخيًا. يتضمن المستودع مراحل توثيق وتصميم قاعدة البيانات وتحليل البيانات وبناء النماذج، إضافة إلى تطبيق سطح مكتب مبني باستخدام `CustomTkinter`.

يقدم التطبيق الرئيسي أربع وظائف تحليلية:

1. **Attack Distribution:** عرض توزيع عدد الهجمات حسب السنة.
2. **Attacks Relationship:** عرض متوسط عدد الوفيات لكل نوع من أنواع الهجمات.
3. **Fatality Prediction:** تقدير عدد الوفيات لثلاثة أنواع من الهجمات باستخدام `LinearRegression`.
4. **Model Comparison:** تدريب ومقارنة `Linear Regression` و`Decision Tree` و`Random Forest` باستخدام `MAE` و`R²`.

كما يوفر التطبيق صندوق إحصائيات سريعة لعرض إجمالي الوفيات، إجمالي الجرحى، عدد الهجمات الانتحارية، والدولة الأكثر استهدافًا.

## المزايا

- توثيق مراحل المشروع من التخطيط وتصميم قاعدة البيانات إلى التقييم.

## مصدر البيانات وبنيتها

يحتاج المشروع إلى ملف CSV باسم:

```text
globalterrorismdb_0718dist.csv
```

لا يوجد ملف البيانات داخل هذا المستودع. يجب الحصول عليه من مصدر مرخص وموثوق، ثم وضعه في مجلد تختاره على جهازك.

الأعمدة التي يستخدمها التطبيق والسكربتات هي:

- `iyear`: سنة الحادثة.
- `attacktype1_txt`: الوصف النصي لنوع الهجوم.
- `nkill`: عدد الوفيات.
- `nwound`: عدد الجرحى.
- `suicide`: هل الحادثة انتحارية، غالبًا بقيم 0/1.
- `country_txt`: اسم الدولة.

قد تحتاج ملفات GTD إلى مراجعة شروط الاستخدام والترخيص قبل إعادة توزيعها أو رفعها إلى مستودع عام.

```bash

```

فعّل البيئة الافتراضية:

```powershell

```


```bash

```


## منهجية النمذجة

### التنبؤ بعدد الوفيات

يقوم `prediction.py` بالخطوات التالية:

1. تحميل `attacktype1_txt` و`nkill`.
2. تحويل `nkill` إلى أرقام واستبدال القيم المفقودة بصفر.
3. حذف النوع `Unknown`.
4. تحويل نوع الهجوم إلى رقم باستخدام `LabelEncoder`.
5. تدريب `LinearRegression` باستخدام نوع الهجوم كمتغير مستقل وعدد الوفيات كهدف.
6. طباعة تقديرات لأنواع `Assassination` و`Bombing/Explosion` و`Armed Assault`.

هذا نموذج تعليمي مبسط؛ استخدام رقم ترميزي لنوع فئوي داخل انحدار خطي لا يعني وجود ترتيب حقيقي بين أنواع الهجمات.

### مقارنة النماذج

يقارن `Model_Comparison.py` بين:

- `LinearRegression`
- `DecisionTreeRegressor(max_depth=5)`
- `RandomForestRegressor(n_estimators=10, max_depth=5)`

يتم تحويل نوع الهجوم إلى أعمدة ثنائية باستخدام `pd.get_dummies`، ثم تقسيم البيانات إلى مجموعة تدريب واختبار. التقييم يتم بواسطة:

- **MAE:** متوسط مقدار الخطأ المطلق بين القيمة الحقيقية والمتوقعة.
- **R²:** مقياس يوضح مقدار التباين الذي يفسره النموذج.

تذكر وثائق المشروع أن شجرة القرار حققت أفضل نتيجة في تجربة سابقة، لكن لا يمكن إعادة إنتاج هذه النتيجة من المستودع وحده لأن ملف البيانات غير مرفق، كما أن النتائج قد تتغير باختلاف إصدار البيانات والإعدادات.

## ملاحظات وقيود معروفة

- المسار الافتراضي للبيانات داخل عدة ملفات مكتوب بشكل ثابت لنظام Windows:

  ```text
  E:\level 3\2\lab\python-mohamed\terrorism attack expecting\globalterrorismdb_0718dist.csv
  ```

  لذلك يجب تعديل `csv_path` أو متغير `path` قبل التشغيل على جهاز آخر.

- زر اختيار ملف مخصص في `main.py` يغير مسار تحليلي التوزيع والعلاقة فقط. أما التنبؤ ومقارنة النماذج والإحصائيات السريعة فتستخدم `self.csv_path` الثابت.
- ملف `phase 8/requirements.txt` موجود لكنه فارغ؛ لذلك تم توثيق الحزم المطلوبة يدويًا في هذا الملف.
- لا توجد اختبارات آلية أو ملفات إعداد مثل `pyproject.toml` أو `requirements.txt` مكتمل.
- يتم تحميل البيانات أكثر من مرة داخل كل وظيفة، وقد يكون ذلك بطيئًا مع ملفات GTD الكبيرة.
- لا يتم حفظ النماذج المدربة، ولا توجد عملية تحقق متقاطع أو ضبط منهجي للمعاملات.
- قد تؤثر القيم الشاذة في `nkill` على نتائج التنبؤ والتقييم.
- يجب استخدام نتائج النموذج لأغراض تعليمية وتحليلية فقط؛ لا تمثل التنبؤات توقعات مؤكدة للحوادث المستقبلية.

## تحسينات مقترحة

- استبدال المسارات الثابتة باستخدام `pathlib.Path` أو ملف إعدادات.
- توحيد مصدر البيانات في متغير واحد داخل التطبيق وتمريره إلى جميع الوظائف.
- إنشاء `requirements.txt` أو `pyproject.toml` مع إصدارات مثبتة.
- إضافة فحص تلقائي للأعمدة المطلوبة ورسائل خطأ واضحة عند اختيار ملف غير صالح.
- استخدام `ColumnTransformer` و`OneHotEncoder` بدل ترميز الفئات يدويًا.
- إضافة تحقق متقاطع ومقاييس إضافية مثل `RMSE`، ومقارنة نتائج التدريب والاختبار.
- حفظ نتائج النماذج والرسوم البيانية، وإضافة اختبارات وحدات لتنظيف البيانات.
- فصل طبقة قراءة البيانات عن الواجهة الرسومية لتسهيل الصيانة والاختبار.
- توحيد أسماء الملفات، مثل إعادة تسمية `relaitonship.py` إلى `relationship.py`.
